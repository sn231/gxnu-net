# 协议分析与方案选择

本文参考本机《技术报告》，整理网页认证如何转为程序实现，以及为什么选择自动重连方案。历史探测来自报告记录，本次文档更新没有发起校园网认证或 UDP 探测；当前实现以仓库源码为准。公开文本不保留真实账号、密码、个人内网 IP 或本地开发路径。

## 1. 先理解认证链路

终端接入校园网络后，认证页面作为用户入口收集凭据。网页认证接口把请求交给服务端认证逻辑，后者校验账号、运营商选择等条件，并使网关建立或调整认证会话。网关按会话和策略放行终端的外网流量。

这里描述的是职责关系。报告及客户端源码不足以确定学校采用何种认证数据库、是否使用 RADIUS、门户与网关如何部署、设备具体如何关联账号和 IP/MAC。客户端能观察的是接口响应，不是这些服务端内部细节。

## 2. 从前端找到协议入口

报告记录先查看门户首页，识别账号字段 `DDDDD`、密码字段 `upass` 和运营商配置；再分析前端 `a41.js` 与 `a40.js`，追踪 `default_login` 如何组装参数、选择登录方法、处理密码及接收响应。

网页中出现的端口和路径不能直接认定为实际登录接口。报告记录 `/eportal/portal/page/loadConfig` 可以提供配置，但尝试 `/eportal/portal/login` 返回协议认证超时；最后采用默认 HTTPS 端口上的 `/drcom/login` 和 `/drcom/chkstatus`。这说明实现时需同时核对前端分支、配置与接口行为。

报告当时记录的配置包括：

| 配置 | 历史值 | 对实现的影响 |
| --- | --- | --- |
| `login_method` | `0` | 采用前端 Dr.COM 登录分支 |
| `en_md5` | `0` | 默认不对密码做应用层 MD5 |
| `account_suffix` | 空 | 不拼运营商后缀 |
| `account_prefix` | `1` | 前端有前缀逻辑，但历史测试与之不一致 |
| `enable_https` | `1` | 默认通过 HTTPS 访问门户 |

这些是历史配置记录，程序不会在每次启动时自动读取 `loadConfig` 并适配所有变化。

## 3. 参数如何映射成 Python

`DrcomClient._build_login_params()` 将配置中的账号、密码和运营商映射为字典；`_get()` 使用 `urllib.parse.urlencode()` 生成查询串，再用 `urllib.request` 发送 GET 请求。

| 参数 | 来源或默认值 | 含义 |
| --- | --- | --- |
| `DDDDD` | 用户账号，默认无前缀 | 校园网账号 |
| `upass` | 用户密码 | 当前默认不做 MD5；可选编码由 `_encode_password()` 处理 |
| `R3` | 用户选择的 `isp` | 0 校园网、1 电信、2 联通、3 移动、4 校园网专线 |
| `0MKKey` | `123456` | 协议常量 |
| `R1` / `R6` / `para` | `0` / `0` / `00` | 前端表单兼容字段 |
| `R2` | 默认空 | MD5 模式下为 `1` |
| `terminal_type` | `1` | PC 终端 |
| `callback` / `v` | 随机生成 | JSONP 回调名称和请求参数 |
| `v4ip` / `v6ip` | 空 | 本实现不显式提交终端 IP |

报告记录带 PC 前缀的账号返回 `userid error1`，裸账号返回 `userid error2`，因此选择默认裸账号。错误码可作为诊断线索，但不能仅凭不同错误码证明服务器内部究竟如何验证账号；其他学校也不一定采用相同格式。

`_parse_jsonp()` 去掉 `callback({...});` 包装后解析 JSON。登录以 `result` 为 `1` 或 `ok` 判断成功；状态查询将在线、离线和无法判定区分后交给守护逻辑。无法解析的响应目前会被转换为 `result=0`，因此有些异常响应也会进入离线判定，这是当前实现的边界。

## 4. 自动化策略为何这样设计

| 问题 | 当前处理 | 原因及边界 |
| --- | --- | --- |
| 偶发网络抖动 | 连续离线确认和快速复查 | 避免单次失败立即重登；会增加确认等待 |
| 门户无响应 | 备用外网 HEAD 探测 | 提供可达性线索，无法保证所有业务都能访问 |
| 重复认证或输错密码 | 滑动窗口限流和错误冷却 | 减少触发网关锁定；内存状态在重启后丢失 |
| 开机时代理未就绪 | `ProxyHandler({})` | 认证及备用探测直连，不依赖代理进程 |
| 网络请求阻塞界面 | 后台线程及 Windows 消息 | 请求由工作线程执行，图标更新交给界面线程 |
| 重复启动 | 进程关系与启动时间检查 | 尽量避开 PyInstaller 父子进程误判；时间阈值方案不能保证所有竞态都被阻止 |

报告提到启动查询失败后“5 次、每次 3 秒”的重试，但当前托盘源码采用周期检测和快速复查，未发现这套独立启动重试流程，因此不把它列为现有功能。

## 5. 网页重连与原生 UDP 心跳的区别

| 方案 | 网页认证自动重连（已实现） | 原生 UDP 登录与心跳（未实现） |
| --- | --- | --- |
| 登录入口 | `/drcom/login` HTTP 接口 | Dr.COM 原生 UDP 登录包 |
| 流程 | 查询状态 → 掉线确认 → 登录 | challenge → login → keep_alive |
| 会话材料 | 当前客户端使用网页接口返回的认证结果 | 通常需 salt、登录响应中的 `AUTH_INFO` 等材料 |
| 常见端口 | 默认 HTTPS 443 | 调研协议使用 UDP 61440 |
| 维护方式 | 掉线后重新认证 | 用匹配原生会话的心跳维护协议状态 |
| 本项目状态 | 代码和离线测试覆盖 | 仅报告中的调研，未完成完整协议实现 |

报告记录收到 UDP challenge 响应，说明当时目标对该类包有响应；这不足以证明学校完整原生登录参数已经确定，更不能保证心跳可以维持网页认证会话。报告研究的原生心跳依赖 UDP 登录响应中的 `AUTH_INFO`，而当前 HTTP 客户端没有取得该材料，所以不能直接拼接一套原生心跳来延长现有网页会话。

要实现另一套认证方式，需要确认学校的协议版本、MAC 处理、包格式及完整登录响应，再独立验证登录与心跳。当前选择网页重连，是因为它对应已分析的网页登录流程，且所需参数已经体现在代码中。

## 6. 不能由现有证据推出的结论

短时间内没有观察到会话变化，不足以证明账号永不限时或永不会被踢。掉线可能与网络切换、学校策略、设备数量或其他原因有关，需进一步观察。程序也无法承诺所有校区或其他学校都适用。

HTTPS 默认开启，但当前关闭证书和主机名校验；密码进入 GET 查询参数。日志、异常和门户响应可能包含敏感内容，因此不能承诺日志绝对不含密码。原始报告中关于隐私的表述应结合后续发布检查理解，详见 [发布前隐私检查](PUBLICATION_REVIEW.md)。
